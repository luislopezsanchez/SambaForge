# ADRs — Architecture Decision Records

> SambaForge. Cada ADR documenta una decisión técnica cerrada, su contexto y justificación.

---

## ADR-001: Stack tecnológico Go + React

**Estado:** ✅ Aceptado  
**Fecha:** 2026-09-09

### Contexto
SambaForge necesita un stack que sea estable, seguro, escalable y que pueda desplegarse como binario único en un controlador de dominio Linux.

### Decisión
- **Backend:** Go 1.23+ con Echo v4
- **Frontend:** React 19 + Vite + TypeScript + Tailwind CSS + shadcn/ui
- **DB interna:** SQLite (modernc.org/sqlite, pure Go)

### Justificación
- Go produce binario único estático, sin runtime externo. Un DC debe ser resiliente.
- Menor superficie de ataque: sin pip/npm supply chain en producción.
- `go-ldap` y `gokrb5` son librerías maduras y validadas en el mismo dominio (go-samba4, Vexa).
- React + Tailwind + shadcn/ui es el estándar actual para paneles admin modernos.
- SQLite sin CGO permite cross-compilation trivial.

### Alternativas descartadas
- **Python (FastAPI):** Requiere runtime Python + pip en el DC. Mayor superficie de ataque.
- **Node.js (NestJS):** Requiere Node runtime + npm en el DC. Mayor consumo de RAM.
- **CGO SQLite (mattn):** Dificulta cross-compilation y Docker scratch.

## ADR-002: Arquitectura local-only

**Estado:** ✅ Aceptado  
**Fecha:** 2026-09-09

### Contexto
SambaForge debe ejecutar `samba-tool` y LDAP contra el servidor Samba AD DC. Necesitamos decidir si SambaForge corre localmente en el DC o remotamente.

### Decisión
SambaForge se instala y ejecuta en el **mismo servidor** que el controlador de dominio Samba.

### Justificación
- `samba-tool` debe ejecutarse localmente para operaciones como provisioning, backup, FSMO.
- LDAP bind local (127.0.0.1:389) es más rápido y seguro que LDAP remoto.
- No requiere abrir puertos adicionales de gestión en el DC.
- Simplifica el deployment: un binario, un servidor.
- Evita la complejidad de un agente remoto (SSH, certificados mutuos, sincronización).

### Alternativas descartadas
- **Arquitectura agente+servidor (como Vexa/NethServer):** Mayor complejidad. Útil para multi-DC pero innecesaria para single-DC inicial.
- **Gestión remota via SSH:** `samba-tool` via SSH añade latencia y requiere credenciales SSH adicionales.

## ADR-003: Modelo de autenticación

**Estado:** ✅ Aceptado  
**Fecha:** 2026-09-09

### Contexto
SambaForge necesita autenticar usuarios contra el dominio Samba AD que está gestionando. Las credenciales no deben persistirse en disco.

### Decisión
- **Login:** LDAP bind con credenciales del dominio (`user@REALM`, password). Usar STARTTLS o GSSAPI.
- **Sesión:** JWT (HS256) firmado con secreto generado al instalar. TTL 8h, renovable.
- **2FA:** TOTP (pquerna/otp) obligatorio para Domain Admins, opcional para otros roles.
- **Credenciales:** Por sesión, en memoria únicamente. Nunca en disco, nunca en DB.
- **Kerberos SSO (futuro):** SPNEGO con gokrb5 para SSO desde el browser.

### Justificación
- LDAP bind valida credenciales reales contra el dominio — no hay users separados de SambaForge.
- JWT sin state en servidor — simple, escalable.
- Cero credenciales almacenadas sigue el patrón de Samba Conductor (zero stored credentials).
- 2FA TOTP es estándar (Google Authenticator compatible).

## ADR-004: Seguridad

**Estado:** ✅ Aceptado  
**Fecha:** 2026-09-09

### Decisión
- **TLS obligatorio.** No HTTP plano. Auto-TLS con Let's Encrypt (Echo) o certificado custom.
- **2FA TOTP** obligatorio para admin.
- **RBAC:** Roles Domain Admin, Helpdesk, Read-only, Self-service.
- **Audit log:** Append-only en SQLite WAL. Registra quién, qué, cuándo, IP. Exportable.
- **Rate limiting:** En login (5 intentos/min) y en API (100 req/min por sesión).
- **Headers:** CSP, HSTS, X-Frame-Options, X-Content-Type-Options.
- **CSRF:** Tokens en forms state-changing.
- **Ejecución de samba-tool:** Passwords via `PASSWD` env var, nunca via CLI args.

## ADR-005: Framework HTTP — Echo v4

**Estado:** ✅ Aceptado  
**Fecha:** 2026-09-09

### Contexto
Decisión entre Gin y Echo para el backend HTTP de SambaForge.

### Decisión
**Echo v4** (`github.com/labstack/echo/v4`).

### Justificación
1. **Auto-TLS nativo:** `e.StartAutoTLS()` integra Let's Encrypt. Crítico para un DC.
2. **Error handling centralizado:** Handlers retornan `error`, middleware central convierte a HTTP.
3. **Middleware built-in:** logger, recover, CORS, JWT, rate limiter, CSRF — todo incluido.
4. **Validado por go-samba4** en el mismo dominio.
5. **Performance equivalente** a Gin (~80k req/s).

### Alternativa descartada
- **Gin:** Mayor ecosistema pero sin Auto-TLS nativo. Acoplamiento mayor a `gin.Context`.

## ADR-006: SQLite driver — modernc.org/sqlite

**Estado:** ✅ Aceptado  
**Fecha:** 2026-09-09

### Decisión
`modernc.org/sqlite` (pure Go, sin CGO).

### Justificación
1. **Sin CGO:** `CGO_ENABLED=0 go build` funciona sin C compiler.
2. **Cross-compilation trivial:** Windows→Linux sin toolchain C.
3. **Docker simplificado:** FROM scratch o Alpine sin librerías C.
4. **Best practice 2026:** Recomendado por la comunidad Go para nuevos proyectos.

## ADR-008: Reverse proxy — Caddy

**Estado:** ✅ Aceptado  
**Fecha:** 2026-09-09

### Decisión
**Caddy** como reverse proxy para SambaForge.

### Justificación
1. **TLS automático:** Caddy obtiene y renueva certificados Let's Encrypt sin configuración.
2. **Config mínima:** 3 líneas para un reverse proxy con TLS.
3. **HTTP/2 y HTTP/3 nativos.**
4. **Binario único** sin dependencias.

### Alternativa descartada
- **nginx:** Requiere certbot + configuración manual de TLS. Más complejo.

### Nota
Echo v4 también tiene Auto-TLS nativo. Para deployments simples (SambaForge directamente expuesto), se puede usar Echo directamente sin Caddy. Para deployments con múltiples servicios en el mismo servidor, Caddy como front proxy.

## ADR-009: Ejecución de samba-tool

**Estado:** ✅ Aceptado  
**Fecha:** 2026-09-09

### Contexto
`samba-tool` es el motor de operaciones de SambaForge. Necesitamos decidir cómo ejecutarlo de forma segura.

### Decisión
1. **Ejecutar como usuario dedicado `sambaforge`** con sudoers restringido a `samba-tool` solamente.
2. **Passwords NUNCA via CLI args** — usar `PASSWD` env var o `KRB5CCNAME` para Kerberos.
3. **Allowlist de subcomandos** — mapear operación → subcomando fijo.
4. **Resolver path absoluto** via `exec.LookPath("samba-tool")` — prevenir PATH planting.
5. **`exec.CommandContext` con timeout** — 30s para operaciones normales, 300s para provisioning/backup.
6. **`--json` cuando esté disponible** — parseo confiable.
7. **`--color=never`** — output limpio sin ANSI.
8. **Capturar stdout y stderr** siempre.
9. **Insertar `--` antes de positionals del usuario** — prevenir flag injection.

### Justificación
- El man page de samba-tool advierte explícitamente contra pasar passwords por CLI.
- sudoers restringido limita el blast radius si SambaForge se compromete.
- El allowlist previene command injection (el usuario no elige qué binario se ejecuta).
